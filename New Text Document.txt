1. H1 verdict: hard GPU-bound. Desktop conclusions invert.
Renderscale delta: 7493.89 µs (18502.83 → 11008.94).

75× the ~100 µs CPU-bound threshold in §4.
510× the reference desktop's 14.7 µs.
§4's prediction that "on a 24-EU UHD this prediction is expected to fail" is confirmed.

And this run identifies the mechanism directly rather than by inference. Comparing the A2/B2 tables, the delta does not land in CPU work — it lands in the fence:

Frame pacing at sys_framepacing_drain 2 is the CPU blocking on the N−1 GPU fence. Quadrupling the pixels quadrupled that wait (2.5 ms → 10.0 ms) while CPU-side buckets barely moved. This is GPU backpressure measured, not deduced — and it sidesteps §2.4's limitation, since the pacing bucket captures the stall that child buckets structurally cannot.

Corroborating: Postproc/resolve scales 11.8× (9.82 → 115.75 µs) — the resolve blit r_renderscale exists to feed, the one stage that scales on both source and destination.

Consequence: r_renderscale 2 must not be the shipped default on hardware like this. Dropping to 1 buys +68% frames (54 → 91 fps) for 4× fewer pixels.

Testing methodology
Three traps cost real runs before the numbers above were trustworthy — the first two are not in BENCHMARK.md and should be added:

defer must be UNQUOTED. Cmd_In_f does cmd = Cmd_Args() (common/cmd.c:274), which preserves the quote characters, so §1's template defer 30 "cl_idlefps 0" pushes one quoted token into the cbuf and dies as Unknown command "cl_idlefps 0". It fails per-command while the run still completes and quits cleanly — it looks like a successful benchmark that produced no numbers. Always grep qconsole.log for Unknown command before believing a result. ruleset_allow_in 1 must also be set un-deferred at the top, since the defer calls register at exec time.
You must spawn in. +map alone leaves you on the team-select screen, whose camera drifts in position. timerefresh sweeps yaw so it normalises angle but not origin — three of my runs were corrupted this way, inflating frame times 16–41% (worst: 32.75 → 23.29 ms) and blowing run-to-run spread to 36–52%. Fixing the origin brought spread to 0.5–9.5%. The failure mimics §2.5 thermal drift, so it's easy to explain away.
§2.6's 100-frame window is long here. At ~50 fps that's ~2 s, so I left 9 s between changing a cvar and dumping (~450 frames) rather than the 2 s the doc suggests.
Every sample verified in-log: cvar values echoed before each dump, noclip on confirmed, zero Unknown command. Interleaved A/B/A/B/A/B in one session, no restarts (§2.5). mp_roundtime is in minutes (* 60, sv_main.qc:310) so server.cfg's 50 = 3000 s and cannot fire mid-run; bot_minplayers defaults to 0, so no bots.

Two things the other LLM will want to know: H2 is now runnable on this machine for the first time (the drain cvar exists in this build), and the follow-up I'd prioritise over anything else is r_shadows_res 8192 → 2048. Separate timerefresh work put ~76% of the shadow cost in resolution-independent cascade generation, and Shadow generation is also the disproportionate grower here — two independent methods pointing at the same knob.
